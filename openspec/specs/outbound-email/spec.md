# outbound-email Specification

## Purpose



Defines how the application sends account, program, discussion, and administrative emails through the configured provider while keeping provider credentials private.



## Requirements



### Requirement: Application emails are delivered through Resend

The production and staging applications SHALL submit existing system-generated and administrator-triggered emails through Resend, including password reset, checkpoint status, image review, educational content, requirement reminders, discussion notifications, and bulk campaigns. A successful send operation SHALL preserve existing message subjects, content, templates, and HTML formatting unless separately changed. Administrator campaigns SHALL resolve recipients from exactly one explicitly selected audience: one or more individually selected users, all eligible participant members of one discussion board, or participants enrolled in one program. Campaigns SHALL exclude campaign opt-outs and SHALL NOT accept a mixture of audience types.

#### Scenario: Application sends an existing email

- **WHEN** an existing application action triggers an email and Resend accepts the message
- **THEN** the intended recipient or recipients receive a Resend submission with the existing message purpose and content

#### Scenario: Resend rejects an email submission

- **WHEN** Resend rejects a message or is unavailable
- **THEN** the send operation reports failure to its caller and does not report the message as successfully sent

#### Scenario: Administrator sends to individually selected users
- **WHEN** an administrator selects one or more individual users and submits a campaign
- **THEN** the campaign is sent to those selected users, excluding opted-out recipients

#### Scenario: Administrator sends to a discussion board
- **WHEN** an administrator selects one discussion board and submits a campaign
- **THEN** the campaign is sent only to eligible participant members of that board, excluding administrators, board admins, allies associated with the board's program, partner staff/program coordinators, and opted-out recipients, and the message body includes a link to the selected board appended after the authored content

#### Scenario: Administrator changes the selected discussion board
- **WHEN** an administrator changes the audience from a discussion board to individual users, a program, or another discussion board
- **THEN** the prior automatically appended board link is removed and, when a new board is selected, its link is appended to the message body

#### Scenario: Administrator sends to a program
- **WHEN** an administrator selects one program and submits a campaign
- **THEN** the campaign is sent only to participants enrolled in that program, excluding administrators, allies associated with that program, partner staff/program coordinators, and opted-out recipients

#### Scenario: Campaign audience is absent or mixes audience types
- **WHEN** a campaign request has no audience, has more than one board or program, or combines individual users with a board or program
- **THEN** the backend rejects the request without sending email

### Requirement: Multi-recipient sends address each recipient individually

For a multi-recipient operation in production or staging, the application SHALL submit a separately addressed message for each intended recipient, optionally grouped in Resend batch requests. It SHALL NOT group recipients in the To, CC, or BCC fields of a shared message.

#### Scenario: Production sends a message to multiple recipients

- **WHEN** an existing bulk campaign or notification targets multiple recipients
- **THEN** each recipient is submitted as the sole recipient of an individually addressed message, and no other recipient is exposed in its To, CC, or BCC fields

### Requirement: Campaign email provides unsubscribe handling

Administrator bulk campaigns and educational-content announcements SHALL include a visible unsubscribe link for each recipient and the `List-Unsubscribe` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click` headers. A public one-click endpoint SHALL validate a signed recipient token and persist the recipient's campaign opt-out. Unsubscribe links generated by either environment SHALL target the canonical production endpoint so production remains the shared opt-out authority. Transactional account, reminder, image-review, and discussion-notification email SHALL remain outside this campaign opt-out.

#### Scenario: Recipient unsubscribes from a campaign

- **WHEN** a recipient submits the one-click unsubscribe request or follows the visible campaign unsubscribe link
- **THEN** the application records the recipient as opted out from future campaign messages and returns a clear confirmation

#### Scenario: Campaign is sent after an unsubscribe

- **WHEN** production or staging prepares an administrator bulk campaign or educational-content announcement
- **THEN** it excludes every opted-out recipient, including opt-outs recorded through the other environment

#### Scenario: Campaign message includes unsubscribe controls

- **WHEN** the application submits a campaign message through Resend
- **THEN** the individual message contains a visible unsubscribe link and both one-click unsubscribe headers

#### Scenario: Transactional notification is sent

- **WHEN** the application sends an account, reminder, image-review, or discussion-notification email
- **THEN** campaign opt-out state does not suppress that transactional message

### Requirement: Resend credentials and sender identity are server-side configuration

The production and staging backends SHALL obtain their Resend API key from the `RESEND_API_KEY` environment variable and SHALL use a configured sender address verified for the sending domain. The API key SHALL NOT be included in frontend code, public responses, or committed configuration files. Campaign unsubscribe signing SHALL use the same backend-only `EMAIL_UNSUBSCRIBE_SECRET` in both environments, and staging SHALL use the canonical production preference endpoint when checking campaign eligibility. The sender SHALL use the Metro Atlanta Saves domain; the initial planned address is `no-reply@metroatlantasaves.com`.

#### Scenario: Backend sends with configured credentials

- **WHEN** the backend has a valid `RESEND_API_KEY` and a sender verified by Resend
- **THEN** it submits mail using that sender without exposing the key to the client

#### Scenario: Backend starts without a Resend key

- **WHEN** the backend starts in an environment where `RESEND_API_KEY` is unset
- **THEN** application startup succeeds, but an attempted email send fails explicitly and no SMTP fallback sends the message

#### Scenario: Repository configuration is shared

- **WHEN** a developer or deployment operator configures the Resend key
- **THEN** the key is supplied as a runtime secret and the checked-in environment example contains only an empty or placeholder value

### Requirement: Email links use the active environment's site origin

Application-generated links in outbound emails SHALL use the origin configured for the environment that sends them: `https://metroatlantasaves.com` in production and `https://metro-atlanta-saves.c4g.dev` in staging, including password reset, program progress, staff review, discussion, and educational resource links.

#### Scenario: Email contains an application link

- **WHEN** the application sends an email containing a generated production link
- **THEN** the link resolves on `https://metroatlantasaves.com`

#### Scenario: Staging email contains an application link

- **WHEN** staging sends an email containing a generated link
- **THEN** the link resolves on `https://metro-atlanta-saves.c4g.dev`

### Requirement: Outbound email does not depend on inbound mail hosting

The application SHALL be able to send email through Resend without an inbound mailbox or inbound email integration for `brpatl.com` or `metroatlantasaves.com`. DNS records required by Resend for outbound sending, including a return-path record when configured, SHALL NOT be treated as an inbound mailbox service.

#### Scenario: Old inbound MX routing is removed

- **WHEN** inbound MX routing for `brpatl.com` has been removed
- **THEN** outbound application emails continue to be submitted through Resend and the application does not depend on receiving email at that domain

### Requirement: Staging uses Resend without changing its site hostname

The staging application SHALL use the Resend integration for outbound email with `RESEND_API_KEY` and a verified `MAIL_FROM` configured in its backend runtime. Staging SHALL preserve the original recipient selection except for campaign opt-outs and SHALL NOT redirect or rewrite recipients. This SHALL NOT change the staging hostname, DNS, TLS, or edge routing.

#### Scenario: Staging sends email through Resend

- **WHEN** staging has a valid Resend API key and verified sender configured and an existing action triggers an email
- **THEN** staging submits the email through Resend to the action's originally selected recipients and generated application links use the staging origin

#### Scenario: Staging campaign honors production opt-outs

- **WHEN** staging prepares a campaign for its original selected recipients
- **THEN** it checks the canonical production preference endpoint and excludes addresses that have opted out in either environment, while other generated application links continue to use the staging origin

#### Scenario: Staging cannot check shared campaign preferences

- **WHEN** staging prepares a campaign without the production preference endpoint configured or reachable
- **THEN** the campaign fails before submission rather than risking mail to an opted-out recipient

#### Scenario: Staging starts without a Resend key

- **WHEN** the staging backend starts without a Resend API key
- **THEN** application startup succeeds, but an attempted email send fails explicitly and does not fall back to SMTP
