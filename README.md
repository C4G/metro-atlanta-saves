## Setup the application

This workspace uses [pnpm](https://pnpm.io). If you don't have it yet, enable it through Corepack:

```
corepack enable pnpm
```

Then setup the application locally by running the following commands in order:

```
pnpm install

docker compose -f ./docker-compose.dev.yaml up -d

pnpm exec nx run backend:prisma-migrate

pnpm exec nx run backend:prisma-seed

pnpm exec nx run backend:prisma-generate
```

After running the above commands, you can start serving the application.

## Environment Setup

1. Copy the `.env.example` file to `.env`:

   ```bash
   cp .env.example .env
   ```

2. Update the `.env` file with your specific configuration values:
   - Set database credentials (`POSTGRES_USER`, `POSTGRES_PASSWORD`, etc.)
   - Configure JWT secret
   - Set up mail server details if needed

## Start the app

To start the development client run `pnpm exec nx serve frontend`. Run `pnpm exec nx serve backend` to start server. Open your browser and navigate to http://localhost:4200/. Happy coding!

**NOTE**: When running this project on a Windows machine, to facilitate hot reload and ensure optimal performance use
`WSL 2`.

## Package manager

This workspace uses **pnpm** — `npm install` / `npm ci` are not supported and will produce a
`package-lock.json` that is ignored by git.

| Task                 | Command                       |
| -------------------- | ----------------------------- |
| Install dependencies | `pnpm install`                |
| Reproducible install | `pnpm install --frozen-lockfile` (used in CI) |
| Add a dependency     | `pnpm add <pkg>`              |
| Add a dev dependency | `pnpm add -D <pkg>`           |
| Remove a dependency  | `pnpm remove <pkg>`           |
| Run a local binary   | `pnpm exec <bin>` (replaces `npx`) |
| Run a one-off binary | `pnpm dlx <pkg>` (replaces `npx` for uninstalled packages) |
| Run a script         | `pnpm <script>`               |

The pinned pnpm version lives in the `packageManager` field of `package.json`, so Corepack will
use the right version automatically.

All pnpm settings live in **`pnpm-workspace.yaml`** (pnpm 11 reads its configuration from there
rather than from `.npmrc`). Four are worth knowing about:

- **`nodeLinker: hoisted`** produces a flat, npm-style `node_modules` instead of pnpm's symlinked
  layout. The CD workflow copies `node_modules` verbatim onto the server, and symlinks into the
  pnpm store would not survive that copy.
- **`strictPeerDependencies: false`** is the equivalent of npm's `legacy-peer-deps`, which this
  workspace previously relied on.
- **`engineStrict: true`** makes a Node version outside the `engines` range in `package.json` a
  hard install failure instead of a warning. Note this also applies to dependencies that declare
  their own `engines` range, so a package that hasn't declared support for Node 24 yet will block
  the install.
- **`allowBuilds`** lists which dependencies may run install scripts — pnpm blocks them by default.
  Packages that compile or download native binaries (argon2, sharp, prisma, nx, esbuild, …) are
  opted in; telemetry-only postinstalls stay off. If you add a dependency with a native build step,
  pnpm will tell you it ignored the build — add the package to that list and reinstall.

## Deployment

Production runs on [Coolify](https://coolify.io) as a **single Docker Compose resource** defined by
[`docker-compose.yaml`](./docker-compose.yaml): three services (`frontend`, `backend`, `db`)
and three named volumes. Coolify redeploys on push to `main` and terminates TLS through Traefik.

Both apps are built from the multi-stage [`Dockerfile`](./Dockerfile) at the repo root:

```sh
docker compose build
docker compose up -d
```

Database migrations run automatically: the backend entrypoint
(`docker/backend-entrypoint.sh`) applies `prisma migrate deploy` before the API starts, and
`depends_on: service_healthy` holds it until Postgres is accepting connections.

### Routing

The frontend and API **must stay on one origin** — the Angular client calls root-relative
`/api/...` paths, and the auth cookie is written with `path=/` and no domain, then forwarded
by the SSR interceptor. Traefik routes `/api` to the backend and everything else to the frontend.

### Uploads

User uploads live on volumes rather than in the image, split along a public/private line:

| Volume        | Mounted at                             | Contents                                                     |
| ------------- | -------------------------------------- | ------------------------------------------------------------ |
| `mas-private` | backend `/data/uploads` (rw)           | `images/`, `discussion-images/` — served only via the API     |
| `mas-assets`  | backend `/data/uploads/assets` (rw)    | `logo/`, `introduction/`, `stories/`, `cohorts/`, `educational-content/` |
|               | frontend `/data/assets` (ro)           | same, served publicly at `/assets/*` by the SSR server        |
| `metro-db-data` | db `/var/lib/postgresql/data`        | Postgres                                                     |

Every upload path derives from the `UPLOAD_DIR` environment variable — see
`libs/backend/shared/src/lib/util/upload-paths.ts`. Locally it defaults to a gitignored
`.uploads/` directory at the workspace root. Files under `images/` are private and reachable
only through the authenticated `GET /api/images/:id`; the frontend container has no filesystem
path to them.

Backups of the `db` service are not managed by Coolify's database-backup UI (that only covers
databases created as their own resource) — schedule a `pg_dump` task separately.
